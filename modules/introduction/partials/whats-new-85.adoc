=== Native Encryption at Rest

Couchbase Server 8.5 introduces native encryption at rest, encrypting data as soon as it's written to disk, with no application changes required. This helps you meet compliance requirements, reduces the impact of lost or decommissioned storage, and gives you control over how encryption keys are managed.

==== Why it Matters

* *Simplifies compliance*: Meet PCI-DSS, HIPAA, GDPR, and similar mandates for encryption at rest without changing application logic.
* *Limits breach impact*: If a storage volume, VM image, or backup is lost, stolen, or improperly decommissioned, the data on it remains encrypted and unreadable without the corresponding keys.
* *Gives you control over key management*: Use Couchbase-managed keys for an out-of-the-box setup, or bring your own keys (BYOK) via AWS KMS, Google Cloud KMS, Azure Key Vault, HashiCorp Vault, or other KMIP-compliant systems.
* *Supports ongoing security hygiene*: Configurable key rotation, on-demand re-encryption, and continuous key-health monitoring with alerts help you catch key issues before they become incidents.
* *Meets FIPS 140 requirements*: FIPS 140-compliant operation is available for organizations that require it.

==== Get started

. Set a master password to protect your local key store, which in turn secures KEKs, DEKs, and data on disk.
. Enable encryption via the Web Console or REST API, selecting the scope as bucket, system, or service-generated data.
. (Optional) Connect your own KMS if you want to manage keys yourself instead of using Couchbase-managed keys.
. Set your rotation policy (minimum 7 days) and trigger manual rotation or re-encryption as needed.
. Use Web Console alerts or the REST API from day one to monitor encryption status and key health.

=== Continuous Backup and Point-in-Time Restore (PITR)

Continuous Backup and Point-in-Time Restore (PITR) is now included in Couchbase Server 8.5.
It continuously captures data mutations in the background as they happen, so that you stop losing data in the gap between backups. 

==== Why it Matters

* *Shrinks your recovery point gap*: Traditional scheduled backups leave a window where mutations between runs can be lost.
Continuous backup captures changes as they occur, closing that window.
* *Restores to the exact second*: Rolls back to a precise point in time, right before an accidental deletion, corruption, or bad application write. 
* *Runs without a backup schedule to manage*: Once enabled, continuous backup captures mutations in the background continuously. You will not be building or maintaining a backup calendar for it.
* *Retention you control*: Keep continuous backup data for anywhere from 1 hour up to 60 days, based on how far back you need to be able to restore.

==== Prerequisites
* Ensure your cluster has one or more Magma buckets since continuous backup isn't available for Couchstore buckets.
* Enable *Change History* on the bucket.
Once continuous backup is turned on for a bucket, you cannot disable Change History for the bucket or for individual collections within it.
* Set the Change History retention to at least 15 minutes, or 2× your continuous backup interval, whichever is longer.
* Keep a regular traditional backup schedule (cbbackupmgr or snapshots) running as this provides the baseline that continuous backup restores build on.

==== Get started

. Enable Change History on the bucket as continuous backup requires it. 
Once continuous backup is on, you can't disable Change History (bucket-wide or per collection). 
Set retention to at least 15 minutes, or 2× your planned backup interval, whichever is longer.

. Enable continuous backup on the bucket via the Web Console, the REST API, or the CLI.
Set the storage location, the backup interval in minutes (minimum 2 minutes), and the retention period in hours (up to 1440 hours / 60 days).

. Establish overlap with a periodic backup as PITR needs your continuous and periodic backups to overlap before it can run.
After enabling continuous backup, wait at least one backup interval, then trigger a full or incremental periodic backup using the Backup Service or cbbackupmgr.

. When you need to restore, check the available restore window first.
This returns the earliest and latest timestamps you can restore to.

. Stop continuous backup before restoring as a backup can't run mid-restore.
This is required even when restoring into a different bucket.

. Run the restore, specifying your target timestamp, the traditional backup archive, and the continuous backup location.

. Re-enable continuous backup once the restore completes, so ongoing protection resumes.

=== Rank Fusion for Hybrid Searches

Couchbase Server 8.5 lets you combine vector, full-text, and N1QL query results into a single ranked result set, in one query.
It uses built-in rank fusion functions in the Query Service.

==== Why it Matters

* *Better search relevance out of the box*: Hybrid search such as blending vector similarity with keyword matching or structured filters, consistently beats any single method alone.
Rank fusion lets you combine them with one function call instead of hand-rolled scoring logic.

* *Simpler application architecture*: Merging results from different search types used to mean client-side logic, multiple round trips, and custom scoring code. 
Now it's a single N1QL expression, executed entirely server-side.

* *Tunable to your workload*: Pick the scoring approach that fits. A rank-based blend that doesn't depend on raw score scales, or a weighted approach when you want one signal to dominate.

==== Get started

. Write your individual queries such as the vector search, FTS query, and/or N1QL query you want to combine.
Each should return results with an id and score field.
. Combine with reciprocal_fusion() such as pass an options object (scorer, normalization, weights), followed by your queries as subqueries or CTE/LET variables.
. Tune and iterate to adjust weights, change the scorer, or add normalization to optimize relevance for your workload.

=== Binary Quantization for Vector Indexes

Couchbase Server 8.5 supports Binary Quantization (BQ) as a new quantization option for GSI vector indexes. This is built for the high-dimensional embeddings (768 dimensions and above) that modern embedding models produce.

==== Why it Matters

* *Faster index builds*: Up to ~4x faster than Product Quantization (PQ), so rebuilding or scaling vector indexes takes a fraction of the time. 

* *Lower query latency, higher throughput*: Up to ~4x lower latency and 3x higher throughput on Hyperscale indexes, at Recall@10 ≥ 80%.
* *No larger footprint*: On-disk storage is comparable to, or slightly lower than, PQ.
* *Simpler configuration*: No PQ sub-quantizer tuning required as BQ is designed to perform well out of the box on high-dimensional data.
* *Works with both vector index types*: Available for Composite Vector Index and Hyperscale Vector Index.

==== Get started

. Create a Composite Vector Index with Binary Quantization.
Use the standard CREATE INDEX statement, setting "BQ" as the quantization type in the description field of the WITH clause.

. Create a Hyperscale Vector Index with Binary Quantization.
Use a distinct CREATE VECTOR INDEX statement, not CREATE INDEX.

. Fine-tune with nbit (valid values 1–9) if you need to trade off precision against index size. 


For more information, see [link to the BQ documentation page].


=== Built-in SQL++ Reranking for Vector Search Results

Couchbase Server 8.5 includes a native reranking capability that lets you reorder vector search results using cross-encoder or LLM-based reranking models — directly within your queries, with no external orchestration required. 

==== Why it Matters

* *More accurate results, not just more similar ones*: Vector search optimizes for recall (semantic similarity), but a semantically close document isn't always the best answer to user intent. Reranking closes that gap by applying a more expensive, more accurate relevance evaluation to a smaller candidate set.
* *No more manual workarounds*: Previously, achieving this in Couchbase required stitching together ARRAY_AGG, curl(), and UNNEST to call an external reranker and reassemble results by hand. 
* *A cleaner, declarative interface*: A single built-in function replaces that hand-rolled pattern, and is easier to write, maintain, and optimize.


==== Get started

. Configure model access by setting up credentials for your reranking model provider (external API or hosted model) using the credential store.
. Write a two-stage query to retrieve candidates with vector search, then apply AI_RERANK as a window aggregate to reorder results by relevance.
. Tune your pipeline by adjusting the candidate set size and review the returned scores to balance latency against result quality.

=== cbbackupmgr Support for WORM Object Storage

Make your Couchbase backups tamper-proof. cbbackupmgr now supports Write Once Read Many (WORM)-enabled object storage as a backup destination, so your backup data is protected from modification or deletion for as long as your retention policy requires — enforced at the storage layer, not just by process.

==== Why it Matters

* *Meets regulatory retention mandates*: Satisfy immutability requirements from frameworks like SEC 17a-4, HIPAA, and GDPR without building a workaround outside your backup workflow.
* *Protects backups from ransomware, even with privileged access*: Once written, backup data can't be encrypted or deleted during its retention period by an attacker or a compromised admin account.
* *Makes audits straightforward*: Point to storage-layer enforcement and not internal process, as proof that your backup data hasn't been altered.
* *Removes a layer of custom tooling*: WORM compliance no longer requires third-party tooling or manual workarounds bolted onto the native backup path. It is built into cbbackupmgr directly.

==== Get started
. Enable WORM on your object store by turning on Object Lock (or your provider's equivalent) on the target storage bucket.
Set the retention period you need.
. Point cbbackupmgr at the WORM-enabled bucket by configuring your backup repository with the appropriate cloud credentials and endpoint.
. Back up as usual by running standard cbbackupmgr backup commands.
You do not need to manage immutability separately. It is enforced by the storage layer.
. Restore when needed by running cbbackupmgr restore against the WORM-protected repository following the normal restore procedure.


=== Credential Store

Couchbase Server 8.5 includes a built-in credential store which is a single, secure place to manage the credentials your services use to reach external resources. 
API keys and tokens no longer need to live inside query text, UDFs, or service configs.

==== Why it Matters
* *Eliminates secret sprawl*: One source of truth for external-access credentials, instead of secrets scattered across configurations, query text, and function definitions.
* *Removes the biggest leak risk*: Hardcoded secrets in UDFs or Eventing functions are hard to rotate and easy to leak.
Reference a credential by ID instead, and it's never exposed in your code.
* *Cuts rotation overhead*: Update a credential once, and it propagates automatically to every node and every service that consumes it. 
You don't need to touch each service individually.
* *Access is scoped, not all-or-nothing*: Fine-grained RBAC means a service or user can only consume the credentials they're explicitly authorized to use.
* *Secured and auditable by default*: Credentials are protected by the cluster's encryption-at-rest infrastructure, and every credential operation be it create, update, delete, or access attempt is fully audited.
* *Rotation you can enforce, not just recommend*: Set expiration on a credential so it's rotated on schedule instead of relying on manual process.

==== Get started
. Enable node-to-node and configuration encryption on your cluster since the credential store requires it.
. Create a credential by using the credential store REST API to add a credential with a type (bearer token, basic auth, certificate), an identifier, and an optional expiration.
. Grant permission to the services that need it (Query, Eventing, Analytics, and so on) permission to consume the credential via the credential consumer role.
. Reference it in your workloads by updating your queries, UDFs, Eventing functions, or Analytics links to point to the credential by ID instead of embedding the raw secret.

=== Query Plan Stability 

Couchbase Server 8.5 introduces Query Plan Stability, letting you lock down and persist SQL++ query execution plans, so your critical queries keep running the way you tuned them, even as your schema, indexes, or the optimizer itself change underneath them.

==== Why it Matters
* *No more silent regressions after upgrades*: Optimizer changes can quietly alter execution plans on queries you've already tuned.
Freeze the plan, and an upgrade can't change it out from under you.

* *Protects tuned performance from schema and index changes*: A dropped index or schema change can push the optimizer toward a different and slower plan.
Plan stability lets you decide how that's handled instead of finding out in production.

* *Consistent behavior across restarts and nodes*: Saved plans are automatically reloaded and primed on node startup, so you don't lose prepared-statement consistency after a restart or rebalance.

*You choose the failure mode*: When a saved plan becomes invalid, decide whether the query should fail loudly or fall back to re-optimization instead of an unpredictable default.

* *Survives disaster recovery, not just uptime*: Saved plans are included in cluster backup/restore, so a restore doesn't quietly undo your plan stability setup.

==== Get started

. Enable plan stability by setting the plan stability mode to on via cluster settings.
. Save execution plans for critical queries by using PREPARE [name] SAVE AS <statement> to persist the optimized plan.
. Configure your error policy by deciding whether an invalidated plan should raise an error or silently re-optimize.
. Monitor plan health via query system:prepareds to check saved plans, their persistence status, and validity.
. Include QUERY_METADATA in your backups and make sure your backup strategy covers this bucket so that saved plans survive a restore.

=== JWT Authentication for the Eventing Service

Couchbase Server 8.5 brings your identity provider to the Eventing Service, not just a username and password.
The Eventing Service now supports JSON Web Token (JWT) authentication, so you can manage and call Eventing functions using token-based credentials issued by your external Identity Provider (IdP), instead of relying on basic auth in a federated environment.

==== Why it Matters
* *One identity flow for everything*: Use the same IdP and token flow across Eventing and the rest of your infrastructure, instead of managing a separate set of credentials just for Eventing.
* *Less exposure from leaked credentials*: Short-lived tokens with automatic expiry are inherently safer than long-lived passwords.
* *Fits a Zero Trust architecture*: Every API call is authenticated with a verifiable, scoped token, not a shared static credential.
* *Built for automation*: CI/CD pipelines and orchestration tools can obtain and use tokens programmatically, with no static secrets to store or rotate manually.

==== Get started
. Configure your IdP by setting up a client and users in your external Identity Provider that map to Couchbase RBAC roles.
. Enable JWT validation on the cluster by configuring the JWKS URI, issuer, and audience via ns_server so the cluster recognizes tokens from your IdP.
. Obtain a token by requesting an access token from your IdP using a standard OAuth2/OIDC flow.
. Call Eventing APIs with the token by passing it in the Authorization: Bearer <token> header on any Eventing REST endpoint call.
. Check your JIT provisioning setting before relying on full lifecycle operations.
If your IdP uses JIT provisioning with dynamic group/role mapping, Eventing will block function creation and deletion.
Use jitProvisioning=false if you need full create/deploy/delete access via JWT.

=== File-Based Rebalance for the Data Service

Couchbase Server 8.5 introduces file-based rebalance for the Data Service instead of streaming every individual mutation over DCP to rebuild data on the target node.
It transfers the underlying vBucket data files directly, cutting rebalance time significantly for large datasets.

==== Why it Matters

* *Faster rebalances on large datasets*: Bulk file transfer is far more efficient than replaying mutations one at a time, especially for large buckets with high data density. This shrinks the window where a rebalance is in progress.
* *Less disruption to running workloads*: Lower CPU and memory pressure on both source and target nodes during rebalance means fewer performance hits to the traffic still running against the cluster.
* *Zero configuration to benefit*: Enabled by default with automatic method selection so that you get faster rebalances immediately after upgrading, with nothing to turn on.
* *Matters most when rebalance duration is a pain point*: Scaling out, replacing a failed node, or routine maintenance on clusters with large data volumes are exactly the situations where this meaningfully reduces your operational window.

==== Get started
. Upgrade to start benefiting from file-based rebalance, since it's enabled by default and there's nothing to configure.
. Rebalance as usual by adding, removing, or swapping nodes the way you always do.
The cluster manager applies file-based transfer automatically where it's appropriate.
. Tune a specific bucket if needed by setting dataServiceRebalanceType to auto (the default), preferFileBased, or preferDcp via the bucket REST API.
. Disable file-based rebalance cluster-wide if needed by setting dataServiceFileBasedRebalanceEnabled to false via /internalSettings, which reverts entirely to DCP-based rebalance.

=== XDCR Support for Cloud Native Gateway

Couchbase Server 8.5 lets you replicate across Kubernetes clusters without opening a single pod to the network. XDCR now supports routing replication traffic through the Cloud Native Gateway (CNG), so cross-cluster replication works cleanly in Kubernetes-native deployments, with no direct pod-to-pod connectivity required.

==== Why it Matters

* *No more networking workarounds*: Setting up XDCR between Kubernetes-hosted clusters used to mean VPN tunnels, service meshes, or alternate address configurations just to establish connectivity.
CNG replaces all of that with a single managed ingress point.

* *Fits how Kubernetes network security actually works*: Direct pod-to-pod connectivity between clusters is often impractical or outright disallowed by network policy.
Routing through gateway endpoints means you are not fighting your own security posture to stand up replication.

* *Aligns with Zero Trust and segmentation requirements*: Replication traffic flows through controlled, managed endpoints instead of direct paths between data service pods.

* *One routing model, not two*: If you're already using CNG for client application traffic, replication now follows the same pattern and is one less thing your team has to reason about differently.

* *Nothing lost in the switch*: Filtering, conflict resolution, priority settings, and pause/resume all keep working exactly as before.
CNG changes the path traffic takes, not what XDCR can do.

==== Get started

. Deploy Cloud Native Gateway on both source and target Kubernetes clusters, using the Couchbase Autonomous Operator.
. Point your remote cluster reference at the CNG endpoint.
Use the CNG hostname and port as the target address when configuring the XDCR remote cluster connection, instead of a direct pod address.
. Create replications as usual by setting them up via the UI, CLI, or REST API the same way you always do.
Traffic routes through the gateway automatically.
. Monitor as usual by using existing XDCR monitoring tools and statistics to confirm replication is flowing correctly over the CNG path.

=== Improved Auto-Delete Behavior for Ephemeral Buckets

Couchbase Server 8.5 stops ephemeral buckets from losing more cache data than the memory pressure actually warrants.
Auto-delete is now rate-limited and topology-aware, so a rebalance or failover can no longer trigger an outsized purge of active data.

==== Why it Matters

* *No more surprise over-deletion during rebalance*: When a node temporarily holds mostly replica vBuckets, the old logic could still delete as if most of that memory were reclaimable, purging nearly all active data on a fraction of actual pressure. That's fixed with this version.

* *Predictable data loss instead of burst deletion*: Deletes are now paced instead of firing in a sudden, aggressive purge, so you can reason about how much data survives a memory pressure event instead of being surprised by it.

* *Fewer cache misses from topology changes*: Node additions, removals, and failovers no longer risk unexpectedly emptying active vBuckets, so downstream performance doesn't take a hit just because the cluster reshaped itself.

* *Nothing to configure*: The improved behavior applies automatically to existing ephemeral buckets using the auto-delete policy.
You get more predictable caching behavior the moment you're on this release.

==== Get started

. No action is required, since the improved behavior is automatic after upgrading and existing ephemeral buckets with auto-delete enabled benefit immediately.
. Confirm your eviction policy by checking that the buckets you want this behavior on are set to `NRU ejection` (auto-delete). 
Buckets set to  `no ejection` will keep rejecting writes when full instead of deleting data.
. Watch retention during your next rebalance, where you should see more stable data retention in ephemeral buckets through node additions, removals, and failovers.

=== Index scan/plan report

Couchbase Server 8.5 helps you stop guessing why an index scan is slow.
It now surfaces a detailed index scan report inside your query execution plans, with timing breakdowns, partition behavior, and wait durations across both the index and query service, instead of a single opaque total.

==== Why it Matters

* *Find the actual bottleneck, not just that one exists*: Today's plan shows one number for the whole scan phase.
Instead of guessing, you can now tell whether slowness is disk I/O, network transfer between query and indexer, consistency waits, or scan processing itself.
* *See whether partition elimination is actually working*: Check how many partitions were scanned versus skipped, so you can tell if your partition key strategy is paying off or silently not helping.
* *Right-size indexer nodes with real numbers*: Understand the true cost of your index scans such as CPU, disk IOPS, or memory, instead of provisioning on guesswork.
* *Confirm pushdowns are doing their job*: Verify that group-by and aggregation pushdowns are actually executing at the indexer level, not silently falling back to post-scan processing.
* *Catch regressions before they become incidents*: Use the report's metrics as a baseline, so a schema, index, or topology change that quietly degrades scan performance shows up immediately instead of months later.

==== Get started

. Use EXPLAIN, or set the query profile to timings, to see the detailed scan report in the execution plan output.
. Look for the warning signs such as high disk read durations, elevated wait times, or scatter/gather imbalances across partitions.
. Act on what you find.
** If disk I/O dominates, consider faster storage or index replicas.
** If partition elimination isn't triggering, review your partition key strategy.
** If consistency waits are running high, evaluate whether request_plus is actually necessary for the workload.
. Track it over time by using the scan report as a baseline.
Re-check it after schema, index, or topology changes to catch regressions early.
