= Manage Point-in-Time Recovery (PITR)
:description: pass:q[Point-in-time recovery lets you restore a bucket to the state it was in at a specific time.]
:page-edition: Enterprise Edition
:page-toclevels: 3

[abstract]
{description}
For an overview of continuous backup and point-in-time recovery, see xref:learn:services-and-indexes/services/continuous-backup.adoc[].

== Prerequisites

* Your Couchbase Server account must have the xref:learn:security/roles.adoc#full-admin[Full Admin] or xref:learn:security/roles.adoc#backup-full-admin[Backup Full Admin] role.

* You must have a Magma bucket configured with continuous backup.
For more information about how to configure continuous backup for a Magma bucket, see xref:manage:manage-backup-and-restore/manage-continuous-backup.adoc[].

* Continuous backup must have made at least a single backup to the continuous backup location.
This means continuous backup must have been active for a bit longer than its continuous backup interval.

* You must have periodic backups for the bucket that overlap with its continuous backups.
For more information about how to make your backups overlap, see xref:manage:manage-backup-and-restore/manage-continuous-backup.adoc#backup-overlap[Overlap Continuous and Periodic Backups].

* You must choose which point in time you want to restore the bucket to.
You can choose any moment in the range currently held in the continuous backup location.
If you stopped continuous backup, you can only restore up to the moment you stopped it.

+
For more information about how far back you can restore, see xref:learn:services-and-indexes/services/continuous-backup.adoc#continuous-backup-retention[Continuous Backup Retention].

+
For more information about how to find the range of time backed up by a continuous backup location, see xref:manage:manage-backup-and-restore/monitor-continuous-backup.adoc#get-cont-backup-info[Get Information About a Continuous Backup Location].

* You must have a bucket where you want to restore to.
This can be:
+
--
** The original bucket.
** A new bucket in the same cluster.
** A bucket in a different cluster.
--
+
If you want to restore the bucket to its exact state at the point in time you choose, flush the bucket before restoring.
For more information about flushing buckets, see xref:manage:manage-buckets/flush-bucket.adoc[].

* To prevent consistency issues, stop continuous backup on the bucket you're restoring.
You must stop continuous backup even if you're not restoring to the original bucket.
Once the PITR finishes, you can restart continuous backup.
For more information about how to stop continuous backup for a bucket, see xref:manage:manage-backup-and-restore/manage-continuous-backup.adoc#stop-continuous-backup[Stop Continuous Backup].

NOTE: You do not need to stop traditional periodic backups or XDCR for the bucket when performing PITR.

== Restore to a Point in Time

You use the `cbcontbk` command line tool to restore a bucket backed up using continuous backup to point in time.

When calling `cbcontbk`, you must supply the following arguments:

`--target`::
The date and time you want to restore the bucket to in an https://www.rfc-editor.org/info/rfc3339/[RFC3339 timestamp^].

`-u`, `-p`::
The username and password for the full administrator.

`--tmp-dir`::
A temporary directory `cbcontbk` can use when restoring data.

`-l`::
The continuous backup storage location.
This is either:
+
* The absolute path to the backup storage location's Network File System (NFS) mount point on all nodes.
* The URI of the cloud storage location.

`-a`::
The filesystem path or S3 URI storing the traditional backup repository.

`-r`::
The UUID for the repository containing the bucket's traditional backup.

`-c`::
The URL for a node in the cluster running the Backup Service.

NOTE: If you're restoring to an empty bucket or you want the bucket's existing documents to be in the state they were in at the time you're restoring to, add the `--force-updates` flag.
This flag can make the PITR faster by turning off conflict resolution.
For more information, see <<#pitr_force_updates>>.

You must also supply credentials `cbcontbk` can use to authenticate with the continuous backup location and the traditional backup repository if they're stored in the cloud.
If you have encrypted backups, you must also supply credentials to decrypt them.
For more information, see the xref:continuous-backup:cbcontbk.adoc[`cbcontbk`] documentation.

=== PITR Example

Suppose you want to restore the `travel-sample` bucket that uses locally mounted NFS shares for continuous backup and traditional backup.
Also suppose you want to restore to the original bucket and want it to be in the state it was in at your chosen restoration time.
In this case, you can follow these steps to perform the PITR:

. Stop continuous backup for the bucket using the command line:

+
[source,bash]
```
couchbase-cli bucket-edit --cluster couchbase://localhost \
              --username $USERNAME --password $PASSWORD \
              --bucket travel-sample \
              --continuous-backup-enabled 0
```

. In this example, the goal is to have the bucket to be the exact state it was at your chosen recovery time.
Therefore, you must flush the bucket before performing PITR.

+
If the bucket does not have flushing enabled, you must first enable it:

+
[source,bash]
```
couchbase-cli bucket-edit --cluster couchbase://localhost \
              --username $USERNAME --password $PASSWORD \
              --bucket travel-sample \
              --enable-flush 1
```

+
Then flush the bucket:

+
[source,bash]
```
couchbase-cli bucket-flush --cluster couchbase://localhost \
              --username $USERNAME --password $PASSWORD \
              --bucket travel-sample
```

+
For more information about flushing buckets, see xref:manage:manage-buckets/flush-bucket.adoc[].

+
NOTE: After finishing PITR, consider turning off the ability to flush the bucket to prevent accidental data loss.

. Before performing the restore, verify the point in time you want to restore to is available in the continuous backup location.
You can find the range of times you can restore to using the `cbcontbk` command line tool:

+
[source,bash]
```
include::manage:example$continuous-backup.sh[tag=get-backup-info]
```

+
The result of the previous command looks like the following:

+
[source,log]
```

```

+
The result in the example shows that you can restore to any point in time between June 6th at 14:57 GMT and June 23rd at 17:55 GMT.

. Use the `cbcontbk restore` command to restore the bucket.
The following command restores `travel-sample` to the state it was in at June 8th, 2026 at 19:54:10 GMT:

+
[source,bash]
```
include::manage:example$continuous-backup.sh[tag=restore-bucket]
```

+
The output from this command looks like this:

+
[source,log]
```
include::manage:example$continuous-backup.log[tag=restore-output]
```

+
You can see that PITR restores a periodic full backup and possibly multiple incremental backups.
Then it replays mutations from the continuous backup until it reaches the selected point in time.

. After you have finished the PITR, start continuous backup again.
The following example restarts continuous backup on the `travel-sample` bucket:

+
[source,bash]
```
couchbase-cli bucket-edit --cluster couchbase://localhost \
              --username $USERNAME --password $PASSWORD  \
              --bucket travel-sample \
              --continuous-backup-enabled 1
```

[#pitr_force_updates]
== PITR Performance and Conflict Resolution

After restoring periodic backups, a PITR replays mutations to restore the bucket to the state it was in at your chosen point in time.
By default, as it replays mutations, it performs Compare and Swap (CAS) checks to avoid overwriting changes to documents that are currently in the bucket.
This behavior prevents PITR from overwriting existing data in documents, so you can perform a PITR while keeping mutations to documents that happened after the point in time you're restoring to.

The CAS checks can make the PITR slower than a standard recovery.
The PITR performs these checks for each mutation it restores.
Each CAS check must read the document to determine if the mutation would overwrite existing data.
PITR on buckets where the metadata does not fit in memory (such as buckets with `fullEviction` eviction policies) can be especially slow.
The extra disk reads caused by CAS checks make the PITR slower.

If you do not need to preserve changes to existing documents or you're restoring to an empty bucket, use the `cbcontbk` command's `--force-updates` flag.
This flag improves PITR's performance by having it skip CAS checks.
Instead, PITR replays the mutation even if it overwrites data already in the bucket.
