= Configure External Collection Options
:description: pass:q[External collections support optional settings that control decimal conversion, historic queries, and storage read parallelism.]
:page-edition: Enterprise Edition
:page-toclevels: 3

[abstract]
{description}

You set these options in the `WITH` clause of a `CREATE EXTERNAL COLLECTION` or `ALTER COLLECTION` statement, or in the equivalent REST API request body.
You can change any of these settings on an existing collection with `ALTER COLLECTION`.

[#convert-decimals-to-doubles]
== Convert Decimals to Doubles

Apache Iceberg's `decimal` type stores an exact, arbitrary-precision numeric value.
Couchbase represents numbers as double-precision floats.
This data type is less precise and cannot represent the full range of an arbitrary-precision decimal.

To prevent any loss of precision, Couchbase returns `decimal` column values as strings.
For example, a `unit_price` column with the value `49.99` returns as the string `"49.99"`, not the number `49.99`.

If you'd rather work with a native number and can accept the possibility of losing some precision, set the external collection's `decimal-to-double` setting to `true`.
You can enable this setting when you xref:manage:manage-scopes-and-collections/create-external-catalogs-and-collections.adoc#create-an-external-collection-using-sqlpp[create the collection], or later by xref:manage:manage-scopes-and-collections/maintain-external-catalogs-and-collections.adoc#alter-an-external-collection-using-sqlpp[altering an existing collection].

The following example creates an external collection with `decimal-to-double` set to `true`:

[source,sql]
----
CREATE EXTERNAL COLLECTION `travel-sample`.`external`.`orders`
ON my_catalog AT my_credential
WITH {
  "namespace": "sales_db",
  "tableName": "orders",
  "decimal-to-double": true
};
----

The following example sets `decimal-to-double` on an existing external collection instead:

[source,sql]
----
ALTER COLLECTION `travel-sample`.`external`.`orders`
WITH { "decimal-to-double": true };
----

With `decimal-to-double` set, the same `unit_price` column returns as the number `49.99` instead of a string.

This setting applies only to the collection where you set it.
You can create 2 external collections that both point to the same catalog and the same Iceberg table, and give each a different `decimal-to-double` setting.
Querying 1 collection returns decimal values as strings, and querying the other returns the same values as numbers.

For more information about creating an external collection, see xref:rest-api:creating-a-collection.adoc#creating-an-external-collection[Creating and Editing a Collection].
For more information about editing an external collection, see xref:rest-api:creating-a-collection.adoc#editing-an-external-collection[Creating and Editing a Collection].

[#perform-historic-queries]
== Perform Historic Queries

For every change made to a table, Apache Iceberg creates a https://iceberg.apache.org/docs/latest/maintenance/[snapshot^].
A snapshot represents the state of a table at the moment of a specific commit.
Snapshots let you query the table as it was at a specific moment in time.
Couchbase gives you 2 ways to query historic snapshots.

Apache Iceberg does not expire snapshots automatically.
Many production tables run periodic maintenance jobs that expire older snapshots to control storage costs, so a table's actual snapshot history often only covers a recent window, not its full lifetime.
Whether a given historic snapshot is still available depends on how the Iceberg table's data pipeline manages retention.

[#query-a-snapshot-in-a-single-statement]
=== Query a Snapshot in a Single Statement

To perform a single historical query, use the `AT SNAPSHOT` or `AT TIMESTAMP` clause in a query of an external collection:

* `AT SNAPSHOT` takes a literal integer snapshot ID.
* `AT TIMESTAMP` takes either a literal integer (Unix epoch milliseconds) or a literal RFC 3339 timestamp string.
When you use `AT TIMESTAMP`, Couchbase queries the most recent snapshot committed at or before that timestamp.
It never returns a snapshot from after the timestamp you specify.

The expression you provide must be a static value.
You cannot use a named parameter, a positional parameter, a subquery, or a function call in an `AT SNAPSHOT` or `AT TIMESTAMP` clause.

The following example queries the `orders` external collection as it existed at midnight UTC on June 1, 2026:

[source,sql]
----
SELECT o.* FROM `travel-sample`.`external`.`orders` AS o
AT TIMESTAMP "2026-06-01T00:00:00Z";
----

You can only use these clauses on external collections, and you cannot use them inside a subquery.
If your query joins more than 1 external collection, each collection can specify its own independent `AT` clause.

The following example joins the `orders` collection at a specific snapshot ID with the `shipments` collection at a specific point in time:

[source,sql]
----
SELECT o.*, s.status
FROM `travel-sample`.`external`.`orders` AS o AT SNAPSHOT 5688794825202065870
JOIN `travel-sample`.`external`.`shipments` AS s AT TIMESTAMP "2026-06-01T00:00:00Z"
ON o.order_id = s.order_id;
----

[#pin-a-collection-to-a-snapshot]
=== Pin a Collection to a Snapshot

If you need to run multiple historic queries, you can set `snapshotId` or `snapshotTimestamp` in the collection's `WITH` clause.
This setting makes all queries on the external collection use the same snapshot.
This saves you from having to repeat an `AT` clause on every query.

The following example pins the `orders` external collection to the snapshot that was current at midnight UTC on June 1, 2026:

[source,sql]
----
ALTER COLLECTION `travel-sample`.`external`.`orders`
WITH { "snapshotTimestamp": "2026-06-01T00:00:00Z" };
----

Every query against the collection now reflects that fixed point in time, until you alter the setting again.

NOTE: You pin the external collection once when you create or alter it.
If the Iceberg table expires its snapshots, your external collection will eventually return errors when the snapshot it's pinned to expires.
For the error you'll see, and how to resolve it, see xref:manage:manage-scopes-and-collections/troubleshoot-external-collections.adoc[].

== Adjust Query Parallelism

By default, Couchbase fetches a table's data from the storage backend a single file at a time.
This behavior prevents querying Iceberg tables from consuming too much network bandwidth and causing latency issues with other Couchbase Server operations.
However, it also limits the performance of external collections.
You can increase the number of files that Couchbase Server transfers in parallel from the external collection's storage location using the `parallelScans` setting.
Set this value to greater than 1 to fetch multiple files concurrently instead.

This setting is separate from the Query Service's general parallelism settings, such as `maxParallelism`.
A query against an external collection always runs as a single operation at the Query Service's execution level, regardless of the `parallelScans` value.
Only the work of fetching files from the storage backend runs in parallel.

The following example sets `parallelScans` to `4` for the `orders` external collection:

[source,sql]
----
ALTER COLLECTION `travel-sample`.`external`.`orders`
WITH { "parallelScans": 4 };
----
