## Configuration Overview

To use credentials to the credential store:

. Make sure your cluster meets the <<prerequisites,prerequisites>> for using the credential store.
. Add at least 1 credential to the credential store.
. Grant access to the credentials by:
** Granting users or groups access to a credential.
** Directly granting a service access to a credential.

[#prerequisites]
## Prerequisites

Before you can use the credential store, your cluster must meet all of the following requirements:

* All nodes in the cluster must be running Couchbase Server 8.5 or later.
The credential store does not work in mixed mode when any node in the cluster is running a version prior to 8.5.0.

* To create or alter credentials, your user account must have the xref:learn:security/roles.adoc#full_admin[Full Admin], xref:learn:security/roles.adoc#credential_admin[Credential Admin], or xref:learn:security/roles.adoc#security_admin[Security Admin] roles.

* Your cluster must have node-to-node encryption enabled.
This setting is not on by default.
This requirement protects the credentials as they're passed between nodes.
To learn how to enable node-to-node encryption, see xref:manage:manage-nodes/apply-node-to-node-encryption.adoc[].

* Your cluster must have encryption at rest enabled for configuration files. 
This encryption is on by default. 
This requirement prevents unauthorized parties from reading the credential store's secure data directly from disk. 
Once you have created a credential in the credential store, Couchbase Server prevents you from turning off encryption at rest for configuration files. 
For more information about encryption-at-rest, see xref:learn:security/native-encryption-at-rest-overview.adoc[].

NOTE: You can override the last 2 requirements. 
Only do so in test or development environments. 
Always use node-to-node encryption and encryption at rest for configuration files to secure credentials in production systems.
To learn how to override these requirements, see <<override-credential-store-requirements>>.

## Manage Credentials Using the Couchbase Server Web Console

You can view, add, and edit credentials using the Couchbase Server Web Console's *Credentials* page.
Open this page by clicking menu:Security[Certificates].

image::manage-security/credential-store/credentials-page.png[align=left]

### Add a Credential Using the Couchbase Server Web Console

To add a new credential to the credential store:

. On the *Credentials* page, click btn:[Add Credential].

+ 
image::manage-security/credential-store/add-credential-dialog.png[align=left]

. In the *Add Credential* dialog, enter an ID and optionally a description for the credential.
The ID is how users refer to the credential when using it with Couchbase Server services. 
It can be up to 128 characters long and can only contain printable ASCII characters other than space and tab.

+
NOTE: While you can include symbols such as `*`, `#`, `?`, and `%` in an ID, the ID is used as part of the URI when making REST-API calls.
It's cleaner to limit symbols in IDs to URI-safe characters such as `/`, `_`, and `-`.

+
While not required, you may want to use a path-like naming convention to organize your credentials in a hierarchy.
For example, you can use IDs such as `query/rest-apis/weather` and `backup/aws/s3`. 
This naming convention makes granting access to multiple credentials using wildcards easier.
For example, suppose you named several credentials following the previous examples.
Then you could grant a user access to all REST-API related credentials by using `query/rest-apis/*` or all backup-related credentials using `backup/*`.

. Under the *Enter Credentials* section, select the *Type* of credential you want to create.
Most of the entries in this field are based on external host provider (AWS or Couchbase, for example).
In some cases, there are several types for a single provider. 
For example, Azure has several subtypes.

.. Optionally choose to the credential expire at a specific date and time.
For more information about credential expiration, see xref:learn:security/credential-store.adoc#expiration[Credential Expiration].

.. Choose which services can use the credential on behalf of the user. 
For more information, see xref:learn:security/credential-store.adoc##allowed-services[Which service can use the credential on behalf of a user].

+
NOTE: If you do not select at least 1 service under *Allowed Services*, users cannot the credential even if you grant them access.
Users do not directly use credentials. 
Instead, they rely on a service to use it on their behalf.
If you do not authorize a service to use the credential on a user's behalf, users cannot use it.

.. If the credential will authenticate with URLs, decide which sites are valid.
Select *All Access (allow all URLs)* to allow users to use the credential to authenticate with any site they choose.
Otherwise, enter a list of URLs the user can authenticate with. 
Optionally add a list of endpoints within the allowed URLs that the user cannot authenticate with.
For more information, see xref:learn:security/credential-store.adoc#url-restrictions[URL and endpoint restrictions].


. Click btn:[Add Credential] to save the credential.

### Viewing and Editing Credentials Using the Couchbase Server Web Console

To view a credential's details or edit it, click *Edit* in the credential's entry 
on the Credential's page. 

You cannot change the ID or type of a credential. 

IMPORTANT: When you edit a credential, the fields containing secret information (such as AWS's *Secret Access Key* field and HTTP's *Token* field) are blank. 
Once you have set a secret value, Couchbase Server never displays it again.
When editing a credential, you must re-enter the secret values again even if you want to keep the existing values.
If a secret field is required, you must enter a value in it before you an save the credential.

## Manage Credentials Using the REST API

Use the `/settings/credentials/{credential_id}` endpoint to add, retrieve, edit an drop credentials in the credential store.

### Add a Credential Using the REST API

You must always supply the credential ID as a path parameter in the URI.
A `curl` command that calls the endpoint to add a credential looks like this: 

[source,bash]
----
curl -u $CB_USER:$CB_PASS -X POST \
     'http://{HOST}:{PORT}/settings/credentials/<credential-id>' \
     -H 'Content-Type: application/json' \
     -d '{
           "type": "<credential-type>",
           "description": "<text>",
           "expiresAt": <epoch-ms>,
           "fields": {<type-specific-fields>},
           "guardrails": {<guardrail-definition>}
         }'
----

* `type` is a required string the sets what authentication provider the credential is for. See the next section for details.
* `description` is an optional text description.
* `expiresAt` is 
* `fields` is an object that contains the settings for the credential.
Its contents depend on the value you set in `type`.
* `guardrails` is an object that sets limitations on the credential's use. 

The following sections describe the `fields` and `guardrails` objects.
