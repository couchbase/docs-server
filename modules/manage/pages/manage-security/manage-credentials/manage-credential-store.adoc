= Manage the Credential Store
:description: The credential store securely holds credentials that Couchbase Server services and users need to access external resources such as REST APIs and cloud storage.
:page-toclevels: 2
:page-edition: Enterprise Edition


[abstract]
{description}
For an overview of the credential store, see xref:learn:security/credential-store.adoc[].

== Configuration Overview

To add credentials to the credential store:

. Make sure your cluster meets the <<prerequisites,prerequisites>> for using the credential store.
. Add at least 1 credential to the credential store.
. Grant access to the credentials by:
** Granting users or groups access to a credential.
** Directly granting a service access to a credential.

[#prerequisites]
== Prerequisites

Before you can use the credential store, your cluster must meet all of the following requirements:

* All nodes in the cluster must be running Couchbase Server 8.5 or later.
The credential store does not work in mixed mode when any node in the cluster is running a version prior to 8.5.0.

* To create or alter credentials, your user account must have the xref:learn:security/roles.adoc#full-admin[Full Admin], xref:learn:security/roles.adoc#credential-admin[Credential Admin], or xref:learn:security/roles.adoc#security-admin[Security Admin] roles.

* Your cluster must have node-to-node encryption enabled.
This setting is not on by default.
This requirement protects the credentials as they're passed between nodes.
To learn how to enable node-to-node encryption, see xref:manage:manage-nodes/apply-node-to-node-encryption.adoc[].

* Your cluster must have encryption at rest enabled for configuration files. 
This encryption is on by default. 
This requirement prevents unauthorized parties from reading the credential store's secure data directly from disk. 
Once you have created a credential in the credential store, Couchbase Server prevents you from turning off encryption at rest for configuration files. 
For more information about encryption-at-rest, see xref:learn:security/native-encryption-at-rest-overview.adoc[].

NOTE: You can override the last 2 requirements. 
Only do so in test or development environments. 
Always use node-to-node encryption and encryption at rest for configuration files to secure credentials in production systems.
To learn how to override these requirements, see <<override-credential-store-requirements>>.

=== Add a Credential Using the Couchbase Server Web Console

To add a new credential to the credential store:

. Open the *Credentials* page by clicking menu:Security[Credentials].
. Click btn:[Add Credential].

+ 
image::manage-security/credential-store/add-credential-dialog.png[align=left]

. In the *Add Credential* dialog, enter an ID and optionally a description for the credential.
The ID is how users identify the credential when using it with Couchbase Server services. 
It can be up to 128 characters long and can only contain printable ASCII characters other than space and tab.

+
NOTE: While you can include symbols such as `*`, `#`, `?`, and `%` in an ID, the ID is used as part of the URI when making REST-API calls.
It's cleaner to limit symbols in IDs to URI-safe characters such as `/`, `_`, and `-`.

+
While not required, you may want to use a path-like naming convention to organize your credentials in a hierarchy.
For example, you can use IDs such as `query/rest-apis/stocks` and `backup/aws/s3`. 
This naming convention makes granting access to multiple credentials using wildcards easier.

=== Viewing and Editing Credentials Using the Couchbase Server Web Console

To view a credential's details or edit it, click *Edit* in the credential's entry 
on the *Credentials* page. 

You cannot change the ID or type of a credential. 

IMPORTANT: When you edit a credential, the fields containing secret information (such as AWS's *Secret Access Key* field and HTTP's *Token* field) are blank. 
Once you have set a secret value, Couchbase Server never displays it again.
When editing a credential, you must re-enter the secret values again even if you want to keep the existing values.
If a secret field is required, you must enter a value in it before you can save the credential.

== Manage Credentials Using the REST API

Use the `/settings/credentials/{credential_id}` endpoint to add, retrieve, edit, and drop credentials in the credential store.

[#rest-api-add]
=== Add a Credential Using the REST API

You must always supply the credential ID as a path parameter in the URI.
A `curl` command that calls the endpoint to add a credential looks like this: 

[source,bash]
----
curl -u $CB_USER:$CB_PASS -X POST \
     'http://{CB_HOST}:{CB_PORT}/settings/credentials/<credential-id>' \
     -H 'Content-Type: application/json' \
     -d '{
           "type": "<credential-type>",
           "description": "<text>",
           "expiresAt": <epoch-ms>,
           "fields": {<type-specific-fields>},
           "guardrails": {<guardrail-definition>}
         }'
----

* `type` is a required string the sets what authentication provider the credential is for. See the next section for details.
* `description` is an optional text description.
* `expiresAt` is an optional integer that sets when the credential expires.
Its value is in milliseconds since the UNIX epoch (midnight January 1st 1970).
* `fields` is an object that contains the settings for the credential.
Its contents depend on the value you set in `type`.
See <<type-fields>> for more information.
* `guardrails` is an object that sets limitations on the credential's use.

For detailed information about adding a credential using the REST API, see xref:rest-api:security/credential-store/manage-credentials.adoc#create-credential[Create a Credential].

The following sections describe the `fields` and `guardrails` objects.

[#guardrails-object]
==== Guardrails Object

The optional `guardrails` object limits how a user can use a credential.
If you do not supply it, users authenticate using the credential.
It can only be used by services you directly grant permission to use the credential.
For more information, see xref:learn:security/credential-store.adoc#guardrails[Guardrails].


[source,json]
----
"guardrails": {
  "allowedServices": ["<service>", "..."],   
  "urlWhitelist": {
    "allAccess": <true|false>, 
    "allowedUrls": ["<url-prefix>", "..."],  
    "disallowedUrls": ["<url-prefix>", "..."] 
  }
}
----

All of the fields in this object are optional. 

* `allowedServices` is a list of strings that sets the Couchbase Server services that can use the credential on behalf of the user. Valid entries in this list are: `n1ql` (Query Service), `backup`, `index`, `xdcr`, `fts`, `eventing`, `cbas` (Analytics Service).
* `allAccess` is a Boolean that controls whether the credential can be used for all URLs.
Defaults to `false`.
* `allowedUrls` lists URL prefixes the credential can authenticate with.
* `disallowedUrls` is a list of endpoints in the list of allowed URLs that the credential is not allowed to authenticate with.

For example, the following `guardrails` object lets a user call the {sqlpp} `CURL()` function (provided by the Query Service).
It can authenticate with any REST API endpoint below  `https://example.com/rest-apis/` except for `/rest-apis/forbidden-endpoint` or anything below it.

[source,json]
----
"guardrails": {
  "allowedServices": ["n1ql"],
  "urlWhitelist": {
    "allAccess": false,
    "allowedUrls": ["https://example.com/rest-apis/"],
    "disallowedUrls": ["https://example.com/rest-apis/forbidden-endpoint"]
  }
}
----

=== Editing Credentials Using the REST API

You have 2 ways to alter a credential using the REST API: the `PATCH` method and the `PUT` method.
The `PATCH` method lets you modify some information in the credential without having to rewrite all of the fields (including the fields containing secrets).
The `PUT` method entirely replaces the credential with the new values you supply.
It clears any values you do not supply.

==== Using the PATCH Method

If you just want to edit a credential's metadata (its description, expiration, and guardrails) you can make a `PATCH` method to `/settings/credentials/{credential_id}`. 
This method call leaves values that you do not alter unchanged.

NOTE: While `PATCH` allows for in-place modification, if you alter any field in the `guardrails` object, it replaces the entire object.
Therefore, if you want to change some of the guardrail values and keep the others as-is, you must supply all of them in the call.

For detailed information about using the `PATCH` method, see xref:rest-api:security/credential-store/manage-credentials.adoc#patch-credential[Partially Update a Credential].

The following example changes the HTTP credential created in a <<http-example,previous example>>.
It reduces the expiration by 6 months from September 15, 2027 to March 15th, 2027.  
It also adds the Analytics Service (`cbas`) to the list of services that can use the credential on behalf of the user.

[source,bash]
----
curl -u $CB_USER:$CB_PASS -X PATCH \
     "http://${CB_HOST}:${CB_PORT}/settings/credentials/stocks/massive/api-key" \
     -H 'Content-Type: application/json' \
     -d '{
           "expiresAt": 1805068800000,
           "guardrails": {
             "allowedServices": ["n1ql", "cbas"],
             "urlWhitelist": {
               "allAccess": false,
               "allowedUrls": ["https://api.massive.com/"]
             }
           }
         }' | jq
----

==== Using the PUT Method

Using the `PUT` method is almost the same as using the `POST` method.
The exceptions are:

* The credential ID must already exist.
If you attempt to `PUT` to a credential URI that does not exist (for example `/settings/credentials/non-existent-credential`), you'll get an error.
* The `type` you supply in the call must match the `type` of the existing credential.
You cannot change the type of a credential once you have created it.

Otherwise, you can change any value in the `PUT` call.
If you do not supply a replacement value for a populated field in the credential, the `PUT` call wipes the field's previous value.
This includes the secret values.

For detailed information about using the `PUT` method, see xref:rest-api:security/credential-store/manage-credentials.adoc#update-credential[Update a Credential].

The following example alters the AWS credential created in <<aws-example,an earlier example>> by changing its region from `us-east-1` to `eu-west-1`.

[source,bash]
----
curl -u $CB_USER:$CB_PASS -X PUT \
     "http://${CB_HOST}:${CB_PORT}/settings/credentials/iceberg/aws/sales-data" \
     -H 'Content-Type: application/json' \
     -d '{
           "type": "aws",
           "description": "S3 access for the sales-data Iceberg table",
           "fields": {
             "accessKeyId": "AKIAIOSFODNN7EXAMPLE",
             "secretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
             "region": "eu-west-1"
           },
           "guardrails": {
             "allowedServices": ["n1ql"]
           }
         }'
----

=== Deleting Credentials Using the REST API

To delete a credential, make a `DELETE` method call to the `/settings/credentials/{credential-id}` endpoint:

[source,bash]
----
curl -u $CB_USER:$CB_PASS -X DELETE \
     "http://${CB_HOST}:${CB_PORT}/settings/credentials/{credential-id}"
----

=== Create a Credential Using DDL

Use the `CREATE CREDENTIALSTORE` statement to add a credential:

[source,sqlpp]
----
CREATE CREDENTIALSTORE `<id>` WITH {
    "type": "<credential-type>",
    "description": "<text>",
    "expiresAt": <epoch-ms>,
    "fields": {<type-specific-fields>},
    "guardrails": {<guardrail-definition>}
};
----

The content of the `WITH` clause is a JSON object with the same structure as the REST API's payload.
For the structure of the values in this clause, see <<rest-api-add>>.

The following example creates an AWS credential for use with an Apache Iceberg external collection.

CREATE CREDENTIALSTORE `iceberg/aws/sales-data` WITH {
  "type": "aws",
  "description": "S3 access for the sales-data Iceberg table",
  "fields": {
    "accessKeyId": "AKIAIOSFODNN7EXAMPLE",
    "secretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
    "region": "us-east-1"
  },
  "guardrails": {

=== Altering Credentials Using DDL

Altering an existing credential using DDL is similar to creating one:

[source,sqlpp]
----
ALTER CREDENTIALSTORE `<id>` WITH {
  "type": "<credential type>",
  "fields": {
    <type-specific fields>
  },
  "guardrails": {
    <guardrail fields>
  }
};
----

As with `CREATE`, the content of the `WITH` clause is the same as the REST API call's payload. 
For the structure of the values in this clause, see <<rest-api-add>>.

The `ALTER` operation is a full replacement.
If you do not supply a value for a field, any existing value is dropped.

The following example alters the HTTP credential created in an <<ddl-create-example,earlier example>> by adding the Analytics Service (`cbas`) to the list of allowed services.

[source,sqlpp]
----
ALTER CREDENTIALSTORE `stocks/massive/api-key` WITH {
  "type": "http",
  "description": "Massive stock market API",
  "expiresAt": 1820966400000,
  "fields": {
    "authScheme": "bearer",
    "token": "yOuRMaSsIvEaPiKeYgOeShErE1234567890"
  },
  "guardrails": {
    "allowedServices": ["n1ql", "cbas"],
    "urlWhitelist": {
      "allAccess": false,
      "allowedUrls": ["https://api.massive.com/"]
    }
  }
};
----

For more information about this command, see xref:n1ql:n1ql-language-reference/altercredentialstore.adoc[].

=== Delete a Credential Using DDL

Use xref:n1ql:n1ql-language-reference/dropcredentialstore.adoc[`DROP CREDENTIALSTORE`] to delete a credential:

[source,sqlpp]
----
DROP CREDENTIALSTORE `<id>`;
----

For example, to drop the HTTP credential from the credential store: 

[source,sqlpp]
----
DROP CREDENTIALSTORE `stocks/massive/api-key`;
----
