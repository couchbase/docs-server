== Release 8.0 (September 2025)

Couchbase Server 8.0 was released in September 2025.
This maintenance release contains fixes to issues.

== Fixed Issues




=== Cluster Manager

[#dlist-known-issues-80-cluster-manager]


*https://jira.issues.couchbase.com/browse/MB-67106/[MB-67106]*::

Couchbase is addressing issues with its cache miss metrics by renaming and deprecating certain statistics. The current metrics, ep_cache_miss_rate and kv_ep_cache_miss_ratio, are being renamed to remove the word "cache" for improved accuracy, as they do not accurately measure memory/disk cache misses. Instead of introducing new metrics, existing ones will be deprecated since they lack documentation and usefulness due to low variance over time. Customers are encouraged to utilize more interpretable documented metrics from the Data Service instead. The "Miss Ratio" will now represent keys not existing as a ratio over all time, and the deprecated metrics will support the graph until they are fully removed. Additionally, there is a proposal to add a "Disk Lookups" metric in future updates to track operations requiring disk access. A release note will inform users about these changes, and an open ticket will address the UI update to reflect these adjustments.


=== Storage

*https://jira.issues.couchbase.com/browse/MB-60542/[MB-60542]*::

The Couchbase Server 8.0.0-1545 and Couchbase Columnar 1.2.0-1009 builds both incorporate a specific kv_engine commit (fd8914a), which focuses on parsing and dumping the "deprecated" and "notes" fields in the code file gen_stat_definitions.cc. This update is documented under the change MB-60542, with each build explicitly referencing the commit that aims to enhance the handling of these fields. The commit message and linked Jira issue highlight the intention to improve the code's functionality concerning the parsing of these elements. This effort is part of a broader update to maintain and possibly enhance metadata management within the system.

*https://jira.issues.couchbase.com/browse/MB-61385/[MB-61385]*::

The XDCR MB for CAS guardrail in Couchbase introduces a configurable method to handle operations when the CAS value is out of bounds. The system can either fail the write or regenerate the CAS, with a tracking counter for such occurrences. This implementation aims to prevent CAS poisoning and support CAS convergence between source and target documents, addressing concerns over conflict resolution during replication. Two modes are available: "error" (rejecting operations) and "replace" (regenerating CAS), while threshold settings are now configurable for different operations like DCP replication and front-end operations. Improvements include adding a new status code to identify invalid CAS errors and ensuring that XDCR can handle these properly, albeit with potential backward compatibility issues for older clusters. The feature can be dynamically configured via REST API, and changes potentially affect replication scenarios, particularly at threshold and configuration levels.

*https://jira.issues.couchbase.com/browse/MB-65644/[MB-65644]*::

The commit message references [MB-65644](https://jira.issues.couchbase.com/browse/MB-65644), which involves setting the plasma configuration option `enableCompressFullMarshal` to false. This change is scheduled to be closed in version 8.0.0-2905. The adjustment is likely part of broader efforts to optimize or correct functionalities related to data compression and indexing. The commit is a part of ongoing refinements within the Couchbase platform's development cycle.

=== Data Service

[#dlist-known-issues-80-data-service]


*https://jira.issues.couchbase.com/browse/MB-62295/[MB-62295]*::

The Couchbase Server build 8.0.0-1668 includes a key change to use a symbolic link for the audit log file, as referenced in kv_engine commit [db74893](https://github.com/couchbase/kv_engine/commit/db74893ff4dda84876a821364317b4627437758e). This change, under the ticket MB-62295, was validated on build 8.0.0-2236. The current-audit.log now symbolically links to a specific log file, allowing for better file management. Additionally, the same commit is present in the couchbase-columnar-1.2.0-1009 build. Release notes are requested to document this update, which should be transparent to users. The link update makes managing audit logs more efficient without user impact.




=== XDCR

[#dlist-known-issues-80-xdcr]


*https://jira.issues.couchbase.com/browse/MB-66140/[MB-66140]*::

In some scenarios, due to race conditions, changing the filter expression or explicit/migration mapping may cause the replication to fail streaming from the beginning. As a consequence, some Source bucket documents may get missed from being replicated to the Target bucket.

+

This has been fixed in 8.0. It is advised to avoid changing these three replication settings:

* filterExpression
* collectionsExplicitMapping
* collectionsMigrationMode

+

until all nodes in the cluster have been upgraded.


=== Query Service

[#dlist-known-issues-80-query-service]


*https://jira.issues.couchbase.com/browse/MB-62793/[MB-62793]*::

The original limit of one XATTR per KV op was relaxed to a maximum of 16 in KV server version 7.6; this ticket explores extending that relaxation to queries.
+
With this change, users can:


. Use up to 15 XATTR fields in their query.


. CREATE INDEX no longer imposes a limit on the number of XATTR fields that can be indexed.

*https://jira.issues.couchbase.com/browse/MB-63459/[MB-63459]*::

New to 7.7.0 is the ability to manipulate document extended attributes (xattrs) via common SQL++ statements.  

+

INSERT and UPSERT statement OPTIONS may now include an “xattrs” object element detailing additions and changes to the xattrs (omissions do not delete xattrs).  The UPDATE statement now supports SET and UNSET of meta().xattrs.{attribute} elements.


=== Eventing Service

[#dlist-known-issues-80-eventing-service]


*https://jira.issues.couchbase.com/browse/MB-64081/[MB-64081]*::

The issue with Eventing not functioning correctly with App Services was identified as being related to the structure of the Sync Gateway registry objects in cloud deployments on Capella. The registry object, in this setup, is enclosed within a "config" key, unlike the direct structuring in on-prem deployments. This discrepancy caused the Eventing Sync Gateway registry parser to fail. Steps to reproduce the issue include coexisting Sync Gateway 3.2 with Eventing version >=7.6.2 and deploying an Eventing function with R+W source keyspace bindings. Testing revealed this issue had not been encountered in the Capella environment before. Patches are currently under review and testing, with an aim to include fixes in upcoming software versions, targeting November 5 and potentially backporting to version 7.6.4. Clarification was made that previous tests did not cover the scenario of using Eventing in this specific environment, prompting new tests to be added for future pipelines.




=== Index Service

[#dlist-known-issues-80-index-service]


*https://jira.issues.couchbase.com/browse/MB-64982/[MB-64982]*::

When shard affinity is enabled, the indexer internally maps all replicas of an index to an alternateID. If such an alternateID exists on a node outside the list of nodes, instead of preventing replica creation, the system creates a new replica with the same alternateID on different nodes. This leads to rebalance failures on the affected nodes.
