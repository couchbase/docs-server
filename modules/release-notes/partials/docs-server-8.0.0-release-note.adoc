*https://jira.issues.couchbase.com/browse/MB-61385/[MB-61385]*::

SET and DELETE with Meta operations could distort the vbucket max_cas if a faulty CAS value is provided in the operation, setting the vbuckets max_cas to an unusually high or inconsistent value. Inadvertently affecting the Hybrid Logical Clock (HLC) and Last Write Wins (LLW) conflict resolution via XDCR. In certain cases, this resulted in legitimate mutations being skipped or ignored during replication. For this reason, the system now fails front-end operations with a CAS value that exceeds the {{hlc_max_future_threshold}}, default value of 65 minutes, to prevent a vbucket’s max_cas from getting distorted.

=== Views

[#dlist-known-issues-80-views]


*https://jira.issues.couchbase.com/browse/MB-67213/[MB-67213]*::

The misleading "Cache Miss Ratio" metric has been renamed to "Get Miss Ratio" to better reflect its purpose, which indicates the fraction of read operations failing due to the absence of keys in the bucket. This change addresses confusion caused by the term "cache miss," which incorrectly suggested a focus on memory/disk caching. Despite considerations around the visibility of the old stat name in UI and scripts, the name remains unchanged to avoid disrupting user scripts. The updated name aligns with existing metrics terminology, providing clarity for users. This update is included in couchbase-server-8.0.0-3417.

=== XDCR

[#dlist-known-issues-80-xdcr]


*https://jira.issues.couchbase.com/browse/MB-66140/[MB-66140]*::

In some scenarios, due to race conditions, changing the filter expression or explicit/migration mapping may cause the replication to fail streaming from the beginning. As a consequence, some Source bucket documents may get missed from being replicated to the Target bucket.

+

This has been fixed in 8.0. It is advised to avoid changing these three replication settings:

* filterExpression
* collectionsExplicitMapping
* collectionsMigrationMode

+

until all nodes in the cluster have been upgraded.


=== Query Service

[#dlist-known-issues-80-query-service]


*https://jira.issues.couchbase.com/browse/MB-62793/[MB-62793]*::

The original limit of one XATTR per KV op was relaxed to a maximum of 16 in KV server version 7.6; this ticket explores extending that relaxation to queries.
+
With this change, users can:


. Use up to 15 XATTR fields in their query.


. CREATE INDEX no longer imposes a limit on the number of XATTR fields that can be indexed.

*https://jira.issues.couchbase.com/browse/MB-63459/[MB-63459]*::

New to 7.7.0 is the ability to manipulate document extended attributes (xattrs) via common SQL++ statements.  

+

INSERT and UPSERT statement OPTIONS may now include an “xattrs” object element detailing additions and changes to the xattrs (omissions do not delete xattrs).  The UPDATE statement now supports SET and UNSET of meta().xattrs.{attribute} elements.


=== Eventing Service

[#dlist-known-issues-80-eventing-service]


*https://jira.issues.couchbase.com/browse/MB-64081/[MB-64081]*::

Eventing currently encounters issues in cloud deployments with Sync Gateway 3.2 due to differences in how the Sync Gateway registry object is structured compared to on-prem deployments. Specifically, the object is nested within a "config" key within the "_sync" system xattr, causing the Eventing’s Sync Gateway registry parser to fail. The issue occurs when App Services with Sync Gateway 3.2 coexists with Eventing version 7.6.2 or later. Fixes have been proposed and are under review, with a target merge date of November 5. Backporting to version 7.6.4 is planned to resolve this. Tests in Capella indicated the issue wasn't present before testing initiated, indicating this setup's uniqueness.

=== Index Service

[#dlist-known-issues-80-index-service]


*https://jira.issues.couchbase.com/browse/MB-64982/[MB-64982]*::

When shard affinity is enabled, the indexer internally maps all replicas of an index to an alternateID. If such an alternateID exists on a node outside the list of nodes, instead of preventing replica creation, the system creates a new replica with the same alternateID on different nodes. This leads to rebalance failures on the affected nodes.
