
[#release-850]
== Release 8.5.0 (Private Preview)

Couchbase Server 8.5.0 is currently available as a private preview build. For more information, see xref:introduction:getting-started-85.adoc[Getting Started with Couchbase Server 8.5].
These release notes are subject to change before general availability (GA).



[#dlist-fixed-issues-850]
== Fixed Issues




[#dlist-fixed-issues-850-cluster-manager]
=== Cluster Manager

*https://jira.issues.couchbase.com/browse/MB-61479[MB-61479]*::

When an ephemeral bucket gets reprovisioned, this can reduce the number of replicas it has, requiring a rebalance to rebuild them.
An alert is now triggered to let you know that you need to perform this rebalance.

*https://jira.issues.couchbase.com/browse/MB-67213[MB-67213]*::

The _Cache Miss Ratio_ metric name suggested it measured memory or disk caching performance.
In reality, as of version 7.6.2, it was redefined to measure the proportion of read (`get`) operations that fail because the requested key is not present in the bucket at all.
To eliminate this confusion, the metric has been renamed to *Get Miss Ratio*.

*https://jira.issues.couchbase.com/browse/MB-70629[MB-70629]* (also published in the 8.0.1 release notes)::

RBAC groups containing `security_admin_local`, `security_admin_external`, or `ro_admin` roles were not handled correctly on upgrade to 8.0.
The upgrade handling now replaces:
+
--
* `security_admin_local` with `security_admin` + `local_user_admin`
* `security_admin_external` with `security_admin` + `external_user_admin`
* `ro_admin` with `ro_admin` + `ro_security_admin`
--
+
The issue also occurred when restoring users from a backup taken on a release prior to 8.0.

*https://jira.issues.couchbase.com/browse/MB-70951[MB-70951]*::

The following stats were reported twice by the `/metrics` REST API.
This has been corrected so each is reported only once: `cm_rest_request_enters_total` and `cm_rest_request_leaves_total`.

*https://jira.issues.couchbase.com/browse/MB-72985[MB-72985]*::

Prior to Totoro, the Cluster Manager supported two ways to set `rebalanceMovesPerNode` in the REST API, a tunable that governs the number of vBucket moves performed simultaneously during a rebalance.
The setting has been removed from the `internalSettings` endpoint, since it also exists in the better-documented and supported `settings/rebalance` API.
This API supports a range of values between 1 and 64, although Couchbase does not recommend changing the value from the default without comprehensive performance testing in a non-production environment.




[#dlist-fixed-issues-850-security]
=== Security

*https://jira.issues.couchbase.com/browse/MB-68379[MB-68379]*::

The default list of TLS cipher suites accepted by the server has been restricted to only include `AES-256-GCM`, `AES-128-GCM`, and `CHACHA20-POLY1305`.
This removes the use of SHA1 and the CBC mode for TLS.

*https://jira.issues.couchbase.com/browse/MB-73874/[MB-73874]*::

A new internal setting, `internalIdentityPasswordCheckUnderMtls`, makes a client certificate carrying the internal identity (`internal@internal.couchbase.com`) no longer sufficient to authenticate as that identity -- the request must also carry valid credentials.
The setting is on by default; in an upgraded cluster, it turns on once the cluster compatibility version reaches 8.5, unless it was set explicitly before.
As a result, adding a node with client certificate authentication now also asks for the administrator's username and password.




[#dlist-fixed-issues-850-data-service]
=== Data Service

*https://jira.issues.couchbase.com/browse/MB-61385/[MB-61385]* (also published in the 7.6.12 release notes)::

`SET` and `DELETE` with Meta operations could distort a vBucket's `max_cas` if a faulty CAS value was provided in the operation, inadvertently affecting the Hybrid Logical Clock (HLC) and Last-Write-Wins (LWW) conflict resolution via XDCR.
In certain cases, this resulted in legitimate mutations being skipped or ignored during replication.
The system now fails front-end operations with a CAS value that exceeds the `hlc_max_future_threshold` (default 65 minutes), to prevent a vBucket's `max_cas` from getting distorted.

*https://jira.issues.couchbase.com/browse/MB-68779[MB-68779]*::

The `kv_ep_commit_time_total_seconds` statistic was reported 1000x too small, because the underlying counter was accumulated in milliseconds while being declared as microseconds.
The counter now uses microseconds.

*https://jira.issues.couchbase.com/browse/MB-69568[MB-69568]*::

The bucket state named `clients` tracked all sorts of clients currently holding a reference to the bucket, including other subcomponents within the same process iterating over buckets.
A new stat, `curr_bucket_connections`, has been introduced to track client connections specifically.

*https://jira.issues.couchbase.com/browse/MB-70471[MB-70471]*::

The `magma_max_default_storage_threads` and `magma_flusher_thread_percentage` bucket configuration parameters have been removed.
These values have been set via their memcached global-settings equivalents since 7.6.10, so setting them through a bucket's extra config string no longer has any effect.

*https://jira.issues.couchbase.com/browse/MB-70640[MB-70640]* (also published in the 7.6.12/8.0.2/8.0.3 release notes)::

Fixed a rebalance hang observed during node scaling and swap rebalance operations, related to socket receive buffer management on specific Linux kernels.

*https://jira.issues.couchbase.com/browse/MB-72266[MB-72266]*::

The Data Service no longer explicitly sets the socket receive buffer size by default -- the behavior introduced in 7.6.12 and 8.0.2 -- and again relies on the operating system's socket buffer auto-tuning, with explicit buffer limits available through configuration where required.

*https://jira.issues.couchbase.com/browse/MB-74199/[MB-74199]*::

Documents that were stored compressed and carried extended attributes (xattrs) could be streamed over DCP with an incorrect datatype.
When a DCP connection requested a document's xattrs without its body, the server decompressed the document and discarded the body before sending, but the resulting mutation still advertised the Snappy datatype bit even though the payload on the wire was uncompressed.
A DCP consumer that acted on the advertised datatype and attempted to decompress the payload could treat the mutation as corrupt and drop it, so the change was never delivered to the consumer.
Affected releases are 7.6.0 through 7.6.12 and 8.0.0 through 8.0.3.




[#dlist-fixed-issues-850-query-service]
=== Query Service

*https://jira.issues.couchbase.com/browse/MB-68969[MB-68969]* (also published in the 8.0.1 release notes)::

* With multi-collection indexes that contained fields with the `include in _all` setting enabled, there was a possibility for false positives to show up for field-agnostic (composite field) queries. This has been addressed by denying sargability for such indexes.
* Addressed an issue where fields not belonging to a particular keyspace were being included in multi-collection indexes.
* Addressed a bug that could influence composite field (`_all`) availability based on the order in which fields were processed.

*https://jira.issues.couchbase.com/browse/MB-69081[MB-69081]* (also published in the 8.0.1 release notes)::

To retrieve a document's expiration, the user had to specify the sub-path explicitly, for example `META().expiration`.
A call to the `META()` function without the sub-path would always incorrectly return the default expiration value of 0.
+
Now, when a query invokes `META()` without explicitly specifying the subpath, the document's expiration value is returned.

*https://jira.issues.couchbase.com/browse/MB-69083[MB-69083]* (also published in the 8.0.1 release notes)::

A query could return an incorrect result when all of the following conditions were met:
+
* the query contains one or more joins
* one of the joins involves a sub-query (FROM clause subquery)
* the FROM clause sub-query has a `GROUP BY` and/or aggregates
* the FROM clause sub-query can take advantage of index group/aggregate pushdown (this requires an appropriate secondary index)
* CBO is on, and `UPDATE STATISTICS` has been run on all keyspaces/indexes involved

*https://jira.issues.couchbase.com/browse/MB-69955[MB-69955]* (also published in the 8.0.1 release notes)::

`CYCLE` was added as a keyword for `RECURSIVE WITH`'s `CYCLE` subclause.
This caused a syntax error when a path or subpath's case-insensitive identifier was named `cycle`.
This is now handled by allowing `cycle` as a permitted identifier.

*https://jira.issues.couchbase.com/browse/MB-70112[MB-70112]* (also published in the 8.0.1 release notes)::

When a prepared request was made with the `auto_execute` request parameter set to `true`, the request would incorrectly error out with `Unrecognizable prepared statement - cause: JSON unmarshalling error: auto_execute did not produce a prepared statement`.
The server now silently ignores the `auto_execute` request parameter when the request is a prepared request.

*https://jira.issues.couchbase.com/browse/MB-70543[MB-70543]* (also published in the 7.6.11/8.0.1 release notes)::

Execution of a scope-level UDF (user-defined function) could fail with an `Invalid Function` error when a query node was starting (and not being upgraded from an earlier version), a scope-level UDF already existed, and a call to execute it was issued shortly after the query node started.

*https://jira.issues.couchbase.com/browse/MB-73773[MB-73773]*::

When `ORDER BY SPARSE_VECTOR_DISTANCE(...)` (or `APPROX_VECTOR_DISTANCE()`) was used without a `LIMIT` clause, the query optimizer incorrectly pushed the vector scan down to the ANN index, causing only a fraction of matching documents to be considered and severely degrading recall.
Vector indexes are now only considered sargable for ANN ordering when a `LIMIT` clause is present.




[#dlist-fixed-issues-850-index-service]
=== Index Service

*https://jira.issues.couchbase.com/browse/MB-67016[MB-67016]*::

A query using a Hyperscale Vector Index could return fewer rows than the `LIMIT` specified, even when the index contained enough matching vectors.
This could happen with vector-only queries as well as queries with filter predicates on include columns.
In both cases, the number of candidate vectors the index returns is bounded by the number of centroids probed (`nprobes`) multiplied by the number of vectors returned from each centroid (`topNScan`, default 40); when `LIMIT` exceeds `nprobes × topNScan`, the result set is capped at roughly that product regardless of the `LIMIT` value.
When filter predicates are present, candidates that don't satisfy the filter are discarded, so the query can return even fewer rows.
For example, with `nprobes` set to 90 and `topNScan` set to 20, a query with `LIMIT 10000` returns about 1,800 results.
If a query returns fewer results than expected, increase `nprobes`, `topNScan`, or both, so that `nprobes × topNScan` is at least the `LIMIT` value -- both can be set per query as optional arguments to `APPROX_VECTOR_DISTANCE`.

*https://jira.issues.couchbase.com/browse/MB-70968[MB-70968]*::

Deleted indexes present on shared files could leave some encrypted data on disk whose encryption keys were no longer tracked.
This data is now deleted asynchronously from disk.

*https://jira.issues.couchbase.com/browse/MB-71712[MB-71712]*::

During index file-based rebalance, if a cluster had buckets with mixed encryption levels (one bucket with encryption enabled, another disabled), the encrypted bucket could temporarily show as having unencrypted data during the rebalance.
This resolves itself once the rebalance completes.




[#dlist-fixed-issues-850-search-service]
=== Search Service

*https://jira.issues.couchbase.com/browse/MB-55637[MB-55637]*::

Before this fix, the Search service exited with a fatal error if writing index data to disk failed, for example with no space left on device, making Search unavailable on that node.
Now, errors while saving index data to disk (persisting) or while removing old index files (cleanup) are logged as errors and the Search service keeps running; other searches on the node keep working.
Indexing on the affected index can't make progress until disk space is freed.
Search still exits on internal panics and configuration-parsing errors.

*https://jira.issues.couchbase.com/browse/MB-68681[MB-68681]*::

When you create a Search index, the number of index partitions (`planParams.indexPartitions`) can no longer be higher than the number of vBuckets in the source bucket, since each index partition must cover at least one vBucket.
A request that goes over this limit now fails with HTTP 400 and the message `rest_create_index: cannot create index with <N> partitions, source bucket '<bucket>' has <M> vbuckets`.

*https://jira.issues.couchbase.com/browse/MB-69641[MB-69641]* (also published in the 8.0.1 release notes)::

Before this fix, a vector (KNN) search returned the top K vectors rather than the top K documents.
When one document held several vectors, such as an array of embeddings, the results depended on how the index was partitioned: a multi-partition index could return the same document several times, once for each matching vector, while a single-partition index returned the document once but with a score taken at random from one of its matching vectors.
Search now returns the top K documents instead, each scored by its single best-matching vector and appearing at most once, with the same results however the index is partitioned.
Queries against documents with multiple vectors may now return more distinct documents than before.

*https://jira.issues.couchbase.com/browse/MB-69654[MB-69654]* (also published in the 8.0.1 release notes)::

An index having two fields at different levels, one a normal field mapping and the other a nested field mapping, but with the same name, were treated as the same entity, so creating the index failed if they needed different configurations.
The Search engine now distinguishes between the two fields as separate entities, so each can be configured independently.

*https://jira.issues.couchbase.com/browse/MB-69655[MB-69655]* (also published in the 8.0.1 release notes)::

When indexing multiple vectors in the same field configured to use cosine similarity for scoring, a bug in the normalization function did not treat the multiple vectors in the field as independent entities.
Normalization is now accurate, so scoring is sound and results are as expected.

*https://jira.issues.couchbase.com/browse/MB-69751[MB-69751]*::

A Search index can source data from at most 100 collections by default.
Creating or editing an index that names more than 100 source collections now fails with an error such as `number of source collections: 1000 exceeds limit: 100`.
Existing indexes are not affected by an upgrade and keep working and rebalancing as before; the limit is checked only when an index is created or its definition is changed.
Self-managed clusters can raise or lower the limit for the whole cluster through the Search service's `managerOptions` REST endpoint:
+
[source,console]
----
$ curl -XPUT -H "Content-Type: application/json" -u <user>:<password> <http://<host>>:8094/api/managerOptions -d '{"collectionsLimitPerIndex": "1000"}'
----

*https://jira.issues.couchbase.com/browse/MB-70388[MB-70388]* (also published in the 8.0.1 release notes)::

`docvalues` is a required field for `geopoint` fields.
If it is not provided by the index, it is calculated on demand during query time, which affects query latency.
Fixed an issue where `docvalues` was not set internally for `geopoint` fields.

*https://jira.issues.couchbase.com/browse/MB-70770[MB-70770]* (also published in the 8.0.3 release notes)::

In extremely rare scenarios, document deletions were not consistently reflected in the index, so a small number of documents successfully deleted from the KV layer could continue to persist in the index as stale entries.
This condition is highly infrequent and non-deterministic, and typically affects only a very small number of documents.




[#dlist-fixed-issues-850-xdcr]
=== XDCR

*https://jira.issues.couchbase.com/browse/MB-68340[MB-68340]*::

To allow finer-grained control over the footprint of an individual replication pipeline, the internal settings `UprFeedDataChanLength` and `UprFeedBufferSize` (which applied one value to all replications) are deprecated in favor of a new replication setting, `dcpFlowControlThrottle`.
`dcpFlowControlThrottle` is a percentage (valid range 5-100) applied to the previous default values of both settings, so a single percentage can be specified instead of configuring them individually.
Until all nodes in a cluster are upgraded, new replications and changes to the new settings should be made via the upgraded nodes.

*https://jira.issues.couchbase.com/browse/MB-70444[MB-70444]*::

XDCR from a Community Edition cluster to another Community Edition cluster is no longer supported, and this is now strictly enforced.
New CE-to-CE replications can't be created, and existing CE-to-CE replications can't continue -- they're automatically paused and can't be resumed.

*https://jira.issues.couchbase.com/browse/MB-70844[MB-70844]*::

Starting from version 8.0, a change in KV-engine behavior for `SUBDOC_MULTI_LOOKUP` on locked documents caused a locked document on the target cluster to be misinterpreted by XDCR as always newer than any mutation of the same document key on the source cluster, causing those mutations to be skipped from replication.
It is advised to upgrade all source clusters that replicate ECCV-enabled buckets to a target cluster running 8.0 or higher.

*https://jira.issues.couchbase.com/browse/MB-71244[MB-71244]*::

When pausing or deleting a replication that was replicating to or from a cluster that recently underwent a failover and needed to roll back to 0, a race condition could cause the replication's goroutines to hang indefinitely.
This has been fixed.

*https://jira.issues.couchbase.com/browse/MB-71476[MB-71476]*::

Previously, if a node was rebalanced out of the cluster while a replication was running, the replication and its buckets were deleted, the buckets were re-created with the same name, and the node was rebalanced back in, the node could lack awareness of the deletion and continue to hold stale manifests for the re-created bucket.
This could cause replication issues, such as documents not being backfilled properly once a broken mapping was fixed.
With the fix, nodes in an upgraded cluster correctly handle being rebalanced back in either before or after the replication is re-created.
+
To maintain backward compatibility, an upgraded node can still accept stale manifests from a legacy node that experienced the bug prior to upgrade; until all source-cluster nodes are upgraded, avoid deleting and re-creating a source/target bucket and its replication while any cluster node is rebalanced out.




[#dlist-fixed-issues-850-tools]
=== Tools

*https://jira.issues.couchbase.com/browse/MB-68392[MB-68392]*::

Cloud storage providers require additional permissions to create WORM backups.
If the permissions required to read old object versions and object locks are missing, the user is unable to create or restore WORM backups.

*https://jira.issues.couchbase.com/browse/MB-70255[MB-70255]* (also published in the 8.0.1 release notes)::

Addressed a bug where buckets with cross-cluster versioning enabled (see xref:learn:clusters-and-availability/xdcr-enable-crossclusterversioning.adoc[XDCR enableCrossClusterVersioning]) would cause a backup merge to fail.

*https://jira.issues.couchbase.com/browse/MB-70745[MB-70745]* (also published in the 7.6.11/8.0.3 release notes)::

A restore could fail when CBO (Cost-Based Optimizer) was enabled, an index existed where one of the index keys contained `::` (for example, `SPLIT(<field>, "::")`), `UPDATE STATISTICS` had been run on the index, and a backup taken after that was restored.
This has been fixed.
