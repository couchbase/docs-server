= Validate Certificates Against CRLs
:description: Certificates can be tested against the loaded Certificate Revocation Lists with the REST API, without changing the cluster's configuration.
:page-topic-type: reference
:page-edition: Enterprise Edition

[abstract]
{description}

[#http-method-and-uri]
== HTTP Method and URI

----
POST /settings/crl/diagnostics/validate
----

[#description]
== Description

Checks certificates against the CRLs loaded on the node that receives the request, as if the given policy were in force.
Nothing is changed.
Use it to predict the effect of a policy before enabling it.

* With `certs`, each supplied certificate is checked, including every certificate in a PEM chain.
* Without `certs`, the cluster's own node certificates and client certificates, on all nodes, are checked.

[#curl-syntax]
== Curl Syntax

----
curl -X POST http://<host>:8091/settings/crl/diagnostics/validate -u <username>:<password> \
  -H 'Content-Type: application/json' \
  -d '{"policy": "<Permissive|Require>", "certs": ["<PEM chain or base64 DER>", ...]}'
----

[#parameters]
== Parameters

[cols="1,1,2,1,3"]
|===
| Name | Required | Values | Default | Description

| `policy`
| No
| `Permissive`, `Require`
| `Require`
| Policy to test with

| `certs`
| No
| Up to 100 strings.
Each is either a PEM text containing one or more certificates, or one base64-encoded DER certificate.
| cluster certificates
| Certificates to test
|===

== Required Privileges

`cluster.admin.security!read` (xref:learn:security/roles.adoc#full-admin[Full Admin], xref:learn:security/roles.adoc#security-admin[Security Admin], xref:learn:security/roles.adoc#read-only-admin[Read-Only Admin]).

[#responses]
== Responses

* `200` with results.
* `400` for invalid input: `{"errors": {"certs": "too many certificates"}}`, `"Invalid PEM certificate"`, `"Invalid base64 encoding"`, or `policy` not one of the allowed values.

Each result has a `subject`, a `status` and, when useful, `details`:

[cols="1,3"]
|===
| status | Meaning

| `good`
| Not revoked (a self-signed root shows `details`: `"self-signed root; not CRL-checked"`)

| `revoked`
| Listed on a CRL from its issuer

| `undetermined`
| No usable CRL. `details` explains why, for example `no usable CRL for this certificate`, or lists expired CRLs

| `failed`
| The certificate could not be checked, for example `cert decode error`
|===

[#example]
== Example (Cluster Certificates)

[source,bash]
----
curl -s -u Administrator:password -X POST \
  http://localhost:8091/settings/crl/diagnostics/validate \
  -H 'Content-Type: application/json' -d '{"policy": "Require"}'
----

[source,json]
----
{
  "policy": "Require",
  "usingClusterCertificates": true,
  "certificatesChecked": 6,
  "allAllowed": false,
  "results": [ ... ],
  "disallowed": [
    {
      "node": "10.0.0.2:8091",
      "certificateType": "node_cert",
      "subject": "CN=node2.example.com",
      "status": "undetermined",
      "details": "no usable CRL for this certificate"
    }
  ]
}
----

Enabling `nodeToNode: Require` now would cut off node `10.0.0.2`, because no CRL from its certificate's issuer is loaded.
