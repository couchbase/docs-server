[#failover-types]
== Failover Types

Couchbase supports 2 basic types of failover:

Graceful:: Graceful failover is the process of removing a Data Service node from the cluster proactively, in an orderly and controlled way.
It involves no downtime, and allows applications to continue accessing data.
The process promotes replica vBuckets on the remaining nodes in the cluster to active status, and the active vBuckets on the affected node to dead.
Throughout the process, the cluster maintains all 1024 active vBuckets for each bucket.
+
You can only use graceful failover on nodes that run the Data Service.
If you want to remove a non-Data Service node in a controlled manner, use the removal process. 
See xref:learn:clusters-and-availability/removal.adoc[] for more information.

Hard:: Hard failovers is the process of removing a node from the cluster after the node has become unavailable.
If the failed node was running the Data Service, its active vBuckets are no longer available.
The hard failover process promotes replica vBuckets on the remaining nodes in the cluster to active status to replace these lost vBuckets.
After the hard failover, each bucket once again has a full set of active vBuckets.
+
IMPORTANT: Do not use hard failover on a node running the Data Service that's still responding.
A hard failover disrupts operations such as data writes and replications on a node running the Data Service.
Instead, use graceful failover to take available Data Service nodes out of the cluster.
+
Use xref:learn:clusters-and-availability/removal.adoc[removal] for any type of node.

You must perform a graceful failover manually.
You can also manually perform a hard failover.

You can let Couchbase Server automatically perform hard failovers by enabling automatic failover.
When you enable auto failover, when the Cluster Manager notices that a node has been unreachable beyond a configured threshold, it initiates a hard failover.

[NOTE]
====
During a failover, Couchbase Server promotes some replica vBuckets on the remaining nodes to active status but it does not create new replicas.
As a result, the cluster temporarily loses those replica copies.

In contrast, when you remove a node, the cluster automatically adds new any replica vBuckets to prevent the loss of replicas that would occur during the xref:learn:clusters-and-availability/removal.adoc[removal].
These additional replicas preserves the cluster's data availability level, but increases memory resource usage on the surviving nodes.
====

After any failover, you should perform a xref:learn:clusters-and-availability/rebalance.adoc[rebalance].
This is especially important after a Data Service node has failed over.
The rebalance makes sure there is an optimal ratio of active to replica vBuckets across all remaining Data Service nodes.

[#detecting-node-failure]
== Detecting Node-Failure

You can perform a hard failover after a node has failed.
You can start it manually or let Couchbase Server handle it through automatic failover.

When you enable automatic failover, the Cluster Manager handles failure detection and hard failover initiation.
This happens without administrator intervention.
However, the Cluster Manager does not identify the cause of failure.
Following failover, you must intervene to identify and fix problems.
You must also start a rebalance to return the cluster to a healthy state.

If you do no enable auto failover, you must detect that a failure has occurred and start the hard failover process manually.
While you can rely on manual monitoring, you can also create an externally based monitoring system using the Couchbase REST API.
This system can monitor the cluster, detect problems, and send notifications or trigger a failover itself.

[#failover-and-replica-promotion]
== Failover and Replica Promotion

After a failover, the cluster promotes replica vBuckets on the surviving nodes to active status.
This leaves an imbalance between active and replica vBuckets on the surviving nodes.
Perform a rebalance to correct this imbalance and restore the cluster to a healthy state.

The following examples show the effect of failover and rebalance on the distribution of active and replica vBuckets across a cluster.

Table 1 shows the distribution of data across a cluster of 4 nodes.
One bucket, of 31,591 items, has 3 replicas, meaning there is a 1:3 ratio of active to replica data.

The cluster still counts active and replica vBuckets for the failed over Node 4, but they're not available.
This is why Node 4's values do not have asterisks--it distinguishes them from approximate values.
To compensate the failover, the system has promoted replicas on nodes 1 to 3 to active status.
Their modified numbers and ratios make this evident.
For example, on node 1, the number of active items has increased from 7,932 to 11,000.
The number of replica items has now decreased from 23,600 to 20,500.

The ratio of active to replica vBuckets on nodes 1 to 3 are now 1:2.
This change occurred because the rebalance has reduced the number of replicas for the bucket from 3 to 2.
This 1:2 ratio is correct for the reduced node-count.

[#failover-efficiency]
== Failover Efficiency

The cluster's Orchestrators (also known as the xref:learn:clusters-and-availability/cluster-manager.adoc#master-services[Orchestrators]) determine how efficiently the cluster handles a failover. 
They manage operations that affect the entire cluster such as failover, rebalance, and adding and deleting buckets.

At any given time, only 1 Orchestrator is in charge.
The Orchestrator instances negotiate among themselves to identify and elect an active Orchestrator.
If the elected instance becomes unavailable, another instance takes over.

If the node that hosts the active Orchestrators fails over, the cluster can experience greater latency than when a non-Orchestrator node fails.
The added latency occurs because the remaining Orchestrators have to choose a new active Orchestrator before the cluster can start the failover process.

Co-locating the Orchestrators on a node with high service overhead can also increase failover latency.
For example, co-location with the Data Service can result in unnecessary data latency during failover.

To limit failover latency, the Orchestrators try to locate the active Orchestrator the node with the lowest service overhead. 
When choosing a node to host the active Orchestrator, Couchbase Server weighs the effect of services running on each node. 
Couchbase Server separates the overhead of services into several tiers.
The following list shows the tiers from least to greatest overhead:

. Backup
. Eventing, Query
. Analytics, Indexing, Search
. Data

The system assigns each tier a cost 10 times higher than the previous tier. 
For example, Couchbase Server considers nodes running the Analytics, Indexing, and Search services as having 30&times; the overhead of a node running just the Query Service.
However, it considers nodes running these 3 services 3.33&times; better able to handle the active Orchestrator role than nodes running just the Data Service.

If available, Couchbase Server always chooses the cluster's xref:learn:clusters-and-availability/cluster-manager.adoc#master-services[Orchestrators] to host the active Orchestrator.
Arbiter nodes do not run any services, and are therefore perfect candidates for hosting the Orchestrator.

[#node-removal]
== Node Removal

Node removal uses the rebalance process to remove a node from a cluster in a controlled fashion.
It creates new copies of replica vBuckets on the remaining nodes.
You would otherwise lose these replica vBuckets when you take the selected node offline.
See xref:learn:clusters-and-availability/removal.adoc[Removal] for a conceptual description of node-removal.
For practical steps, see xref:manage:manage-nodes/remove-node-and-rebalance.adoc[Remove a Node and Rebalance].
