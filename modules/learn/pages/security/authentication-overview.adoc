= Understanding Authentication
:description: pass:q[To access Couchbase Server, users must be authenticated. \
_Authentication_ is a process for identifying who is attempting to access a system.]
:page-toclevels: 2

[abstract]
{description}
Once a user is authenticated, _authorization_ decides what they are allowed to do.

== What Authentication Protects

Every way into Couchbase Server requires authentication:

* The *Web Console*, where administrators inspect and change the cluster.
* The *REST API*, used for configuration and management.
* The *CLI* tools, such as `couchbase-cli`.
* *Client connections* from applications built with the Couchbase SDKs.

Not every authentication method covers all four.
See <<comparison,Compare Authentication Methods>>.

Always connect over TLS.
The encrypted Web Console port is 18091; the unencrypted port, 8091, passes credentials in the clear from the browser to the console and is not recommended.
See xref:learn:security/on-the-wire-security.adoc[On-the-Wire Security].

== Available Methods

Couchbase Server groups authentication methods into two kinds.

*xref:learn:security/native-authentication.adoc[Native authentication]* is built into Couchbase Server, which stores the credentials itself:

* Usernames and passwords
* X.509 client certificates

*xref:learn:security/external-authentication.adoc[External authentication]* hands the check to a system you already run:

* PAM, using the Linux host's own accounts
* LDAP, including Microsoft Active Directory
* SAML, for Web Console single sign-on
* JWT, using signed tokens from an identity provider

== Choosing an Authentication Method

*Prefer an external method.*
LDAP and JWT both cover the Web Console, clients, the CLI, and the REST API, so one system can serve your whole cluster.
They give you a single place to grant and revoke access, one password policy across every application, and features Couchbase Server does not provide itself &#8212; multi-factor authentication, self-service password reset, and single sign-on.
That last point matters most in environments where Couchbase Server is one of several applications your users reach.

Revocation works differently under JWT, though.
Removing a user at the identity provider stops it issuing new tokens, but tokens it has already issued remain valid until they expire.
There is no way to cancel a token that is already in circulation, so choose token lifetimes with that in mind.

*Use the special-purpose methods where they fit.*
X.509 client certificates are an excellent choice for applications: they are mutually authenticated, and no credential travels over the network.
SAML is a good choice for Web Console sign-in if you already run a SAML identity provider, though it cannot authenticate applications.
You can combine methods &#8212; certificates for applications and single sign-on for administrators, for instance.

*If you stay with native usernames and passwords*, tighten them up:

* Set a password policy that enforces length and complexity.
See xref:learn:security/native-authentication.adoc#password-strength[Password Strength].
* Issue temporary passwords to new users, so they must choose their own on first sign-in.
See xref:manage:manage-security/manage-native-passwords.adoc#force-password-update[Force Password Update].
* Store credentials with Argon2ID, and disable SCRAM-SHA where you use TLS.
See xref:learn:security/native-authentication.adoc#secure-credential-storage[Secure Credential Storage].

For the practical steps for each method, see xref:manage:manage-security/manage-authentication.adoc[Manage Authentication].

[#authorization]
== Authorization

Couchbase-Server features &#8212; including data, settings, and statistics &#8212; can be accessed only by users who have been assigned the appropriate _privileges_.
Privileges include _read_, _read-write_, _execute_, and _manage_.
Privileges are assigned by _Full_ and _Security_ Administrators, in correspondence with _roles_.
When a user successfully authenticates, their assigned roles are examined, and access is granted or denied by Couchbase Server.

Roles can be assigned to a user in either or both of two ways:

* _Directly_.
The user is associated directly with one or more Couchbase-Server roles.

* _By Group_.
A Couchbase-Server _user-group_ is defined, and roles are assigned to the user-group.
The user is made a member of the user-group, and thereby inherits all the roles of the group.
A user can be a member of any number of groups.

An external authentication provider can also supply a user's groups or roles.
With LDAP group support, the roles assigned to a Couchbase-Server user-group can be inherited by users not defined on Couchbase Server, as described in xref:learn:security/authentication-domains.adoc[Authentication Domains].
JWT can carry a user's roles and groups in the token itself, as described in xref:manage:manage-security/jwt-roles-and-groups.adoc[Assign Roles and Groups from a Token].

See
xref:manage:manage-security/manage-users-and-roles.adoc[Manage Users, Groups, and Roles], for details on creating users and groups, and assigning roles.

[#authentication-domains]
== Authentication Domains

Couchbase Server assigns each user to one of two _authentication domains_: _local_ and _external_.

The _local_ domain contains users defined locally, on Couchbase Server, which stores their credentials.
The _external_ domain contains users whose credentials live elsewhere &#8212; on an LDAP server, a SAML identity provider, a JWT identity provider, or Linux systems accessed by means of PAM.

For a complete overview, see xref:learn:security/authentication-domains.adoc[Authentication Domains].

Some external methods can authenticate a user who has no Couchbase Server account at all.
JWT calls this _just-in-time provisioning_: the token supplies the identity and the permissions, and Couchbase Server creates no account.
See xref:manage:manage-security/jwt-roles-and-groups.adoc[Assign Roles and Groups from a Token].

In addition to a username and password requirement,
SAML can require _Two-Factor Authentication_ (TFA) such as a one-time code sent via text message or a code generated by an authentication module or app.
SAML can also provide _Single Sign On_ (SSO), where a user that has already authenticated with another application is automatically authenticated to use.

[#blocking-user-authentication]
== Blocking User Authentication
[.edition]#{enterprise}#

Administrators can lock user accounts by blocking their authentication.
This is enforced through account locking.
After an account is marked as locked, it prevents the user from logging in or from continuing the existing sessions.
Locking an account terminates all active UI sessions and long-running connections such as Memcached or streaming connections.

[IMPORTANT]
====
* This feature is only available after the entire cluster is upgraded to version 8.0 or later.

* Only local domain user accounts can be locked or unlocked.
External domain user accounts cannot be locked or unlocked.
====

This feature is useful for preventing users from connecting to the database during maintenance.

Administrators can block authentication manually through the UI, REST API, or CLI,
or automatically through inactivity-based locking after a defined idle period (using TTL).
TTL based locking also allows accounts to be blocked temporarily, with automatic unlocking after the configured duration.
By default, automatic blocking rules can exclude System Administrators and other critical roles, to maintain uninterrupted operations.

From the authentication flow perspective, any login attempt against a blocked account is denied,
and the login screen displays a clear error message indicating that the account has been locked.
The server communicates this state consistently across interfaces; UI responses, CLI status, REST API outputs, and SDK error codes all reflect the locked status.

For auditing and compliance, every lock event is logged with details of who performed the action and under what conditions.
This ensures that blocking user authentication is both transparent and reversible while maintaining strong security boundaries.

For more information about locking or unlocking user accounts from the UI, see xref:manage:manage-security/manage-users-and-roles.adoc#lock-and-unlock-user-accounts[Lock and Unlock User Accounts].
